# 存储策略

更新时间：2026-06-03

## 1. 决策

Open Sales Assistant 会继续保留 JSON 文件存储作为一种正式支持的存储模式。

后续数据库能力应通过可选适配器加入，而不是替换当前 JSON 模式。

默认模式：

```env
STORAGE_DRIVER=json
```

计划中的可选模式：

```env
STORAGE_DRIVER=postgres
STORAGE_DRIVER=mysql
```

## 2. 为什么保留 JSON 存储

JSON 存储适合作为开源基础版本，因为：

- 新用户克隆仓库后不需要安装数据库就能运行。
- Demo 数据容易查看、重置和通过 Git 审阅。
- 小团队可以先验证工作流，再决定是否引入生产数据库。
- 贡献者可以用最少环境复现问题和运行测试。
- 对不熟悉服务器和数据库的用户更友好。

JSON 存储不适合高并发生产写入。

## 3. 数据库适配目标

数据库支持应该提升生产可用性，但不能破坏本地运行的简单性。

目标：

- 保留 `data/db.json` 作为默认本地/demo 存储。
- 在当前读写逻辑外抽象一层 storage interface。
- 支持从 JSON 迁移到数据库。
- 备份和恢复行为要明确。
- 不把 API Key 或私有部署密钥存到数据库。
- smoke test 不依赖数据库服务。

## 4. 建议的适配器结构

后续可以把存储逻辑逐步整理为：

```text
server/storage/
  index.js
  json-store.js
  postgres-store.js
  mysql-store.js
```

应用层应调用统一的 storage 方法，而不是在路由中直接读写 `data/db.json`。

初始接口可以包括：

- `readDb()`
- `writeDb(db, options)`
- `createBackup(reason)`
- `ensureDailyBackup()`
- `migrateDb(input)`

## 5. 迁移路径

建议实现顺序：

1. 先把当前 JSON 读写逻辑移动到 `server/storage/json-store.js`，保持行为不变。
2. 在 `.env.example` 中加入 `STORAGE_DRIVER=json`。
3. 增加测试，证明 JSON 模式仍然可用。
4. 增加 JSON 和数据库之间的导入导出/迁移命令。
5. 优先支持 PostgreSQL。
6. 等 storage interface 稳定后，再支持 MySQL。

## 6. 兼容规则

任何数据库相关开发都必须遵守：

- 不移除 JSON 存储。
- `npm test` 不依赖数据库。
- 默认 quick start 不依赖数据库。
- 不提交本地生产数据。
- demo 数据仍然可以通过 Git 或 fixture 重置。
- 文档必须说明什么时候 JSON 足够，什么时候建议数据库。

## 7. 什么时候用哪种模式

适合使用 JSON：

- 本地试用项目。
- 测试 demo 数据。
- 开发新功能。
- 小规模内部 proof of concept。

适合使用数据库：

- 多个团队成员同时写入数据。
- 需要更可靠的备份、恢复、审计和迁移。
- 准备生产部署。
- 需要更大规模的报表、分析或外部系统集成。
